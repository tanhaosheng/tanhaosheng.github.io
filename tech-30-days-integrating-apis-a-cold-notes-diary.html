How this was compiled: This is a first-person diary of a month spent building against APIs, reconstructed from standard engineering practice and official specs (MDN, the OAuth RFCs, Fielding's dissertation). It is a teaching narrative, not a benchmark of any vendor, and no tool is rated.

Day 0, 11 p.m., empty repo

New project. The product needs to talk to three external services. I know "API" loosely. The next 30 days are about making that word concrete. Notes below, written the way I'd write them in a terminal log.

Day 1 — REST is just HTTP with opinions

Fielding's dissertation (2000) defined REST as a set of constraints, not a wire format. In practice: resources have URLs, and GET/POST/PUT/DELETE map to read/create/update/delete. First call:

curl https://api.example.com/users/42 \
  -H "Authorization: Bearer $TOKEN"

Response: JSON. Stateless — every request carries what the server needs. No session cookie required. That single property is why REST scales.

Day 8 — Over-fetching, and the GraphQL counter

The mobile client pulled a user object but rendered three fields. REST handed back forty. That's over-fetching, and on a slow link it adds up. GraphQL lets the client ask for exactly what it draws:

query {
  user(id: 42) {
    name
    avatarUrl
  }
}

One endpoint, one shape. The cost: you now own a query planner and need rate limiting on query depth, or a client can ask for the whole graph in one request. Trade-off, not a free lunch.

Day 15 — Auth is where projects stall

API keys are the lazy option: a static string in a header. Simple, and weak — they leak in logs and repos. For delegated access, OAuth 2.0 (RFC 6749) is the standard: the user authorizes, the service issues a short-lived access token and a refresh token. I implement the authorization-code flow:

GET /authorize?response_type=code
  &client_id=...&redirect_uri=...&scope=read

Then exchange the code for a token. The lesson, repeated by every security write-up on MDN: keep the token server-side, scope it to the minimum, and expire it.

Day 22 — Rate limits are a feature

I got throttled at 429. Fine — that's the server protecting itself. The fix is not "retry instantly in a loop"; it's respect Retry-After, back off exponentially, and paginate list endpoints instead of pulling everything. Pagination is non-negotiable on any real dataset:

GET /orders?limit=100&cursor=abc123

Read the docs for the cursor format; every API names it differently and none of them warn you when you hit the wall.

Day 30 — What I'd tell myself on Day 0

  • Read the status codes like a protocol, not a suggestion: 200 ok, 201 created, 400 bad request, 401 unauthorized, 403 forbidden, 404 missing, 429 too fast, 500 their fault.
  • Validate every input. Injection starts at the boundary.
  • HTTPS only. A token over plain HTTP is a token already stolen.
  • Document as you go. OpenAPI/Swagger turns the contract into something others can read without guessing.
  • Don't reach for GraphQL to fix a problem you don't have. REST over-fetches; it doesn't lie.

Frequently asked questions

REST or GraphQL for a new project?

If your data is resource-shaped and your clients are predictable, REST. If clients vary wildly in what they need and you're over-fetching badly, GraphQL earns its complexity. Don't pick GraphQL because it's fashionable.

Are API keys ever acceptable?

For server-to-server with a secret you control, yes, stored safely. Never ship them in client code. For acting on a user's behalf, OAuth 2.0 is the right tool.

How do I avoid getting blocked?

Honor rate limits and Retry-After, paginate, and cache. The server throttling you is doing its job; the fix is backoff and smaller requests, not louder retries.

Is OpenAPI worth the effort?

Yes, once a second person or a frontend team consumes your API. It turns an implicit contract into a readable, testable one. Skip it only for a throwaway internal script.

Verdict: After 30 days the takeaway is boring and true: an API is a contract, not a feature. REST for resource CRUD, GraphQL when clients truly vary, OAuth 2.0 for delegated access, and rate-limit respect as table stakes. The caveat: no framework removes the discipline — validate input, keep tokens server-side, and document the contract or the next developer pays for your silence.
