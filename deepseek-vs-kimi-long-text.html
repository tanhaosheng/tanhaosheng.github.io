DeepSeek vs Kimi：长文本能力技术对比与选型指南

先想一个具体问题

一份 1,200 页的并购尽调合同，需要在两天内完成条款梳理和风险点提取。你会把它喂给哪个模型？

这不是抽象的"长文本能力"讨论——这是一道有具体约束的工程题：文档多长、预算多少、能不能接受分段、里面有没有图表扫描件。这四个变量基本决定了 DeepSeek 和 Kimi 之间的选择，跟"哪个模型更强"关系不大。

结论可以先给：文档折算后在 256K token 以内、纯文本、预算敏感——选 DeepSeek V4，几乎没有悬念；文档必须整体处理且超过 500K token，或包含大量图表扫描件——才轮到 Kimi K3 出场，但你要先算清成本账。下面是推导过程。

第一步：把"页数"换算成 token

选型讨论经常在这一步就跑偏。厂商宣传用 token 计数，而你手里的文档是按页计的。粗略换算（中文文档，具体取决于分词器和排版密度）：

  • 一页常规中文合同 ≈ 800–1,200 字 ≈ 1,000–1,800 token
  • 256K token（DeepSeek V4 上限）≈ 150–250 页
  • 1M token（Kimi K3 宣称上限）≈ 600–1,000 页

回到开头那份 1,200 页的合同：它超出了两个模型的单次处理能力——DeepSeek 需要切成 5–8 段，Kimi 也大概率需要至少切一次。也就是说，对于极端长文档，"分段 + 汇总"的工程方案无论如何都绕不开，此时百万级窗口的溢价是否值得，就要打个问号。

$0.28 对 $15，单看单价只是个倍数（约 53 倍）；放进月度账单才有体感。假设一个 3 人法务/研究团队，每个工作日让模型输出约 30 万 token 的摘要、条款清单和风险备注（月约 660 万 token 输出）：

这笔账的含义很直接：DeepSeek 的定价低到可以"无脑全文重跑"，而 Kimi 的定价要求你精打细算每一次调用。工程上这是两种完全不同的工作方式——前者可以暴力迭代 prompt，后者每次长文本调用都值得先在小样本上调好再上全量。

架构差异：为什么一个 256K、一个敢标 1M

DeepSeek V4：在"够用的窗口"里做精度

根据 DeepSeek 公开技术报告，V4 处理长文本的思路是混合注意力 + 分段检索增强：长文档分段后用局部注意力抓细节，跨段注意力负责把关键信息串起来，再叠加检索式的加权聚焦。这套设计的取舍很清楚——不追求窗口数字上的震撼，而是保证在 256K 范围内检索精度和速度都不塌。

Kimi K3：用压缩换窗口上限

月之暗面在 K3 发布会上介绍的路线是分层注意力 + 多粒度压缩：先对超长文档做保留语义结构的压缩，再在压缩表示上算注意力，从而把计算复杂度压到可接受范围，同时支持图文混合输入。代价也写在公开评测里：长文本模式速度明显偏慢，且压缩过程理论上存在细节损失的风险。

一句话概括两条路线：DeepSeek 选择把 256K 做扎实，Kimi 选择用压缩技术把窗口撑到百万级。没有谁对谁错，只有和你的文档长度分布匹不匹配。

"上下文窗口" ≠ "有效上下文"：怎么读 NIAH 数据

NIAH（Needle In A Haystack，大海捞针）测试是检验长窗口"含金量"的标准方法：在超长文档的任意位置埋一条关键信息，看模型能否准确找到。公开社区数据的大致图景是：

  • DeepSeek V4：在 256K 全窗口范围内，社区测试普遍反映"针"在开头、中间、末尾都能稳定命中，与官方技术报告口径一致。
  • Kimi K3：500K 以内的公开测试反馈良好；接近百万 token 的区间公开数据很少，部分社区测试提示准确率在超长区间有回落。

这正是"标称窗口"和"有效窗口"的区别：宣称能装下 100 万 token，不等于在第 90 万个 token 处埋的条款还能被稳定召回。如果你的业务对召回率敏感（合同审查漏一条就是事故），建议用自己的文档做一轮埋针测试，方法很简单：在真实文档不同位置插入唯一标识句，然后提问验证。

按画像选

  • 法务/咨询团队，日常处理 200 页以内中文合同 → DeepSeek V4。窗口够用、速度快、成本低到可以忽略，多轮追问不心疼。
  • 研究者，要一次性吞下整本学位论文或 500 页以上报告 → 先试"DeepSeek + 分段汇总"，不满意再上 Kimi K3。分段方案省下的钱通常远超过工程成本。
  • 文档里全是图表、扫描件、图文混排 → Kimi K3。这是它相对 DeepSeek 纯文本路线的硬优势，没有替代方案。
  • 开发者，想要开源权重自己部署 → DeepSeek 系（HuggingFace 有开源模型可用），Kimi 闭源不提供这条路。
  • 预算充足、只要能力上限、不想做任何切分工程 → Kimi K3，但请先按上文成本表核一遍月账单。

FAQ

两者中文能力谁更强？

都是国内头部团队，中文语料占比都很高，纯中文文本理解属同一梯队，日常使用感知差异不大。真正拉开差距的是场景变量：图文混排的中文文档 Kimi 有多模态优势；纯文本长文档 DeepSeek 的性价比和速度占优。

DeepSeek V4 能处理 1000 页的 PDF 吗？

单次不能。256K token 约合 150–250 页中文文档，1000 页需要切成 4–7 段分别处理再汇总。好消息是它的价格让"分段 + 多轮汇总"的总成本依然远低于 Kimi 单次调用；坏消息是你需要自己写分段和汇总逻辑（或用现成的 RAG 框架）。

怎么验证一个模型的长文本能力是不是真的？

三步：① 用自己的真实文档，在不同位置插入唯一标识句做埋针测试；② 记录不同长度下的命中率和响应耗时；③ 交叉参考 LMArena 等公开榜单和 HuggingFace 社区分享。厂商宣称的窗口数字只是入场券，有效召回才是能力。

DeepSeek 是完全开源的吗？

不是"完全"。DeepSeek 在 HuggingFace 上开源了多个系列模型（如 DeepSeek-Coder），可自行下载部署；但最新对话旗舰模型主要通过 API 提供服务。开源程度以其 GitHub 组织页实际发布为准。

结论：把"1M token"当成营销数字之前，先量一下自己文档的真实长度。绝大多数中文长文档场景（合同、论文、报告）折算后落在 256K 以内——这个区间里 DeepSeek V4 以约 1/53 的输出价格、更快的速度和稳定的全窗口召回，是明显更合理的默认选择。Kimi K3 的不可替代性只在两处：必须整体处理的 500K+ 超长文档，以及图文混排的多模态解析。落在这两种场景里，就为它的溢价买单；不在，就别。
