Monday 9 a.m. The branch is broken

The merge succeeded. The tests don't. Nobody remembers which commit was last good. This is the failure Git exists to prevent — not by magic, but by recording every state of every file as an immutable snapshot you can return to. If you only learn one tool as a developer, make it this one.

The landscape: Git is not the only VCS

Git dominates today, but it lives in a field with distinct designs. Know the map before you assume Git is the answer to every problem.

SystemModelBest atWhere it loses
GitDistributed, snapshot-basedAlmost everything; huge ecosystem (GitHub, GitLab)Very large binary repos, monorepos at scale
Mercurial (hg)Distributed, simpler CLIGentle learning curve, large reposSmaller ecosystem, less mindshare
Subversion (SVN)CentralizedStrict central control, linear historyNo offline work; server is a single point of failure
Perforce (Helix)Centralized, enterpriseMassive binary assets (games, chip design)Licensing cost; heavier ops

Git won on distribution: every clone is a full backup, and branching is cheap. That is why it became the default, not because it is simplest.

How Git works, briefly

  • Snapshot, not delta: each commit stores the whole file state (with de-duplication underneath). History is a graph of commits, not a patch list.
  • SHA-1 addressing: every object (blob, tree, commit) is named by a hash. Same content → same hash → tamper-evident.
  • Three areas: working directory → staging area (index) → repository. You choose what enters each commit.
  • Cheap branches: a branch is a pointer to a commit. Creating one is O(1). This is why Git workflows branch constantly.

The commands that actually matter

# start
git init
git clone <url>

# record work
git add .
git commit -m "why this changed, not what"

# branch
git branch feature-x
git switch feature-x
git merge feature-x
git rebase main

# sync
git push origin feature-x
git pull --rebase

The discipline that matters is the commit message. Write the reason. Six months later the diff shows what changed; only the message explains why.

Stated design reasoning

As the project's own history records, Linus Torvalds created Git in 2005 after the free BitKeeper license used for Linux kernel development was revoked. The constraints he set — distributed, fast, integrity-checked — are still the ones Git enforces. The free Pro Git book documents this and the internals in full.

A branching decision map

  • Solo project, shipping continuously: trunk-based. Short-lived branches, merge to main often.
  • Team, scheduled releases: GitHub Flow — main always deployable, features in PRs.
  • Strict release trains (multiple versions live): Git Flow — separate main, develop, release, hotfix branches. More process, clearer control.

Pick the lightest model your team can actually follow. Heavy branching strategy on a 2-person team is pure overhead.

Guardrails

A .gitignore keeps secrets and build junk out of history:

# .gitignore
.env
node_modules/
*.log
dist/

Never commit credentials. Once a secret is in history, deleting the file doesn't remove it — the hash stays. Rotate the secret; rewrite history with git filter-repo.

Frequently asked questions

Git vs GitHub — what's the difference?

Git is the version-control tool. GitHub (and GitLab, Bitbucket) is a hosting service with pull requests, issues, and CI on top. You can use Git with no host at all; the host is optional.

Merge or rebase?

Merge preserves true history (a fork and join). Rebase rewrites commits onto a linear base for a clean log. Rule of thumb: rebase your local feature branch onto main; never rebase commits others have pulled — you rewrite shared history.

Is Git bad for big binary files?

Git stores snapshots, so large binaries bloat the repo over time. For game assets or datasets, use Git LFS or a centralized system like Perforce. Git is not the right tool for 100 GB of media.

How do I undo a commit?

git revert <hash> makes a new commit that undoes it — safe on shared branches. git reset rewrites history — only on work no one else has. Know which one you're using.

Verdict: Git is the default version-control system for good reasons — distributed, integrity-checked, and backed by the largest ecosystem. But it is a tool, not a religion: for massive binary assets, Perforce or Git LFS still win, and SVN still fits teams that want central control. The honest caveat: Git's power comes from discipline (good messages, clean ignores, correct reset vs revert) — the tool won't save a team that commits secrets and rebases shared history.
